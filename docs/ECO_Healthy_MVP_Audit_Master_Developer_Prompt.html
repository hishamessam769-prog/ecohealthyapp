القرار التنفيذي

القرار: لا يجوز تشغيل النسخة الحالية على بيانات عملاء أو مدفوعات حقيقية. الواجهة متماسكة بصرياً، ودورة العرض الأساسية قابلة للتجربة، كما أن المشروع ينجح في البناء الإنتاجي. لكن طبقة الصلاحيات الحالية قابلة لتسريب كامل بيانات العملاء والماليات لأي مستخدم مسجل، ومنطق التحصيل والإيراد والعمولة والإيراد المؤجل غير صالح كدفتر حقيقة مالي. وصف النسخة في README بأنها “Production-ready” غير مدعوم بالأدلة الهندسية.

الـMVP ليس عديم القيمة؛ أفضل توصيف له هو Prototype وظيفي لاختبار رحلة العمل والواجهات. يمكن إعادة استخدام الهيكل البصري، مكونات الواجهة، RTL، بعض مسميات النطاق، والاختيار التقني العام. أما طبقة البيانات والصلاحيات والحسابات والـRealtime والـOffline والاختبارات فيجب إعادة بنائها على أساس جديد، لا ترقيعها بقرارات موضعية.

الخلاصة في سبعة أحكام

  1. الأمن وRBAC مكسوران فعلياً: دالة public.erp_bootstrap() تعمل بصلاحية مالكها وتعيد كل الموظفين والعملاء والطلبات والمدفوعات والاشتراكات والتسويات لكل مستخدم Authenticated، من دون فلترة حسب الدور أو الملكية.
  2. المحاسبة ليست نظام Accounting: لا توجد فواتير محاسبية مستقلة، ولا بنود فاتورة أو تخصيص مدفوعات أو قيود يومية أو دفتر أستاذ أو جدولة إيراد مؤجل أو مطابقة بنك حقيقية.
  3. Live Data ليس Live: التطبيق يحمل Snapshot ضخم مرة واحدة، ثم ينعشه فقط بعد حركة نفذها المستخدم نفسه. لا توجد Supabase Realtime subscriptions ولا polling مضبوط ولا read models حسب الدور.
  4. CRM غير موجود: لا توجد Leads أو محادثات أو قنوات أو حملات أو Spend أو Touchpoints، ولذلك لا يمكن حساب CAC أو Conversion أو Speed-to-lead أو Attribution.
  5. الاشتراكات غير منضبطة: Pause وSkip لا يزحزحان الاستحقاقات ولا يعيدان حساب تاريخ الانتهاء، ولا توجد Subscription cycles أو Entitlement ledger أو Renewal entity.
  6. اللوجستيات شاشة Stops وليست Logistics Engine: لا توجد Routes أو Windows أو Map orchestration أو timestamps كاملة أو POD/OTP أو SLA أو offline mutation queue أو cash handover محاسبي.
  7. الجاهزية للتخارج شبه غائبة: لا توجد Metric definitions أو KPI snapshots أو Cohorts أو investor role أو data masking أو certified close أو access log لغرفة البيانات.

ما نجح ويمكن الحفاظ عليه

  • Next.js/React/TypeScript مضبوط على strict، والبناء الإنتاجي اكتمل بنجاح.
  • RTL حقيقي على مستوى <html dir="rtl" lang="ar">، وواجهة Mobile-first جيدة كبداية.
  • صفحات مفاهيمية مفيدة: العملاء، الطلبات، الاشتراكات، المطبخ، التوصيل، الحسابات، المبيعات.
  • وجود محاولة واضحة لبوابة اعتماد المحاسب قبل التشغيل، وهي نواة صحيحة يجب تحويلها إلى Transaction محكمة.
  • استخدام PostgreSQL وSupabase مناسب للحجم المستهدف إذا أعيد تصميم الصلاحيات والمخطط والمهاجرات.
  • وجود Audit table وRLS وRPCs كبذور تصميم، لكن تطبيقها الحالي لا يحقق Least Privilege أو سلامة التدقيق.
  • PWA manifest وService Worker كبداية شكلية؛ يلزم استبدال منطق الـoffline التشغيلي بالكامل.

التشخيص الفوري: إجراءات الاحتواء قبل أي تطوير

إذا كانت هذه النسخة منشورة أو دخلتها بيانات حقيقية، ينفذ الفريق خلال 24–48 ساعة الإجراءات التالية بالترتيب:

  1. إيقاف Public signup من Supabase Auth وحذف زر إنشاء الحساب من واجهة الإنتاج.
  2. REVOKE EXECUTE عن public.erp_bootstrap() وعن جميع الدوال العامة من authenticated، ثم منح أقل مجموعة لازمة بعد إعادة التصميم.
  3. إلغاء أي Deploy يسمح بـNEXT_PUBLIC_REQUIRE_AUTH=false أو NEXT_PUBLIC_DEMO_MODE=true في Production؛ يجب أن يفشل Build/Startup عند الإعداد الخاطئ.
  4. إزالة مبدّل الدور من Live mode وإجبار الواجهة على قراءة الدور من Server session فقط.
  5. عدم تحميل أي دفعات أو PII جديدة حتى تطبيق read models مفلترة حسب الدور.
  6. تغيير/تدوير Sessions والروابط الموقعة ومراجعة Auth users غير المعروفين؛ ليس لأن تسريباً ثبت، بل لأن مساراً يسمح به موجود.
  7. حذف CacheStorage وService Worker القديم من أجهزة التشغيل عند Logout/Version change؛ الـSW الحالي قد يحتفظ بردود مصادق عليها على جهاز مشترك.
  8. تجميد وظائف collect_cash, verify_payment, set_delivery_status حتى إضافة idempotency والتحقق من الانتقالات والمبالغ.
  9. حفظ نسخة read-only من قاعدة البيانات وسجل Auth/Audit قبل أي إصلاح، حتى لا يضيع دليل التحقيق.

تحليل الـMVP شاشة بشاشة

لوحة الإدارة الحالية

تعرض أربعة أرقام: الإيراد المعتمد تاريخياً، الاشتراكات النشطة، حمل مطبخ الغد، والطلبات المنتظرة. الحساب يتم في Browser على جميع الصفوف التي حملها bootstrap، بلا فترة زمنية أو Currency/Branch أو drill-down. لا توجد CAC/LTV/Churn/Retention/MRR/ARR/Deferred Revenue أو Plan vs Actual، ولا يوجد تمييز بين رقم تشغيلي لحظي ورقم مالي مقفل.

القرار: لا توسع الصفحة الحالية؛ أنشئ CEO read model ومجموعة metric definitions، واجعل كل بطاقة قابلة للضغط للوصول إلى numerator/denominator والصفوف المكونة لها.

الإيجابي أنها تجسد Gatekeeper. لكن “الدليل” مجرد اسم ملف، والدفعة تساوي amount لا Invoice total، والـCash يتحول إلى COD، ثم المندوب نفسه يحوله Verified. “أموال العملاء المتبقية” تقسم العقد على الأيام فقط. الإقفال اليومي يسمح بإدخال Actual cash وإغلاق سجل موجود بلا Journal، بلا Bank statement، بلا maker-checker، وبلا منع إغلاق عند فرق أو مستند Exception.

الحل: Notifications/Tasks server-side، user-targeted، deep links، escalation rules، read/acknowledge events. Offline stores أقل بيانات لازمة ومشفرة قدر الإمكان، مع مسحها عند logout/device revoke.

استخدام anon key من المتصفح مع RLS صالح للقراءات الضيقة، لكنه لا يكفي وحده لرحلات مال معقدة. الـBFF يقدم:

  • التحقق من Session وPermission وBranch وOwnership على Server.
  • حساب السعر والإجمالي من Price Book، لا من payload.
  • مفاتيح Idempotency وتوقيع Webhooks وRate limiting.
  • إخفاء تفاصيل المخطط ومنع mega-JSON.
  • تجميع Query محددة للشاشة من read model لا من كل الجداول.
  • إصدار Audit correlation ID واحد لكل رحلة.

تبقى RLS طبقة دفاع ثانية إلزامية؛ وجود BFF لا يبرر استخدام Service Role بلا ضوابط. وإذا استُخدم Service Role في Job/Integration فيبقى Server-only وبصلاحية محددة وسجل Audit.

قواعد RLS غير القابلة للتفاوض

  1. Default deny لكل جدول جديد؛ الاختبار يفشل إذا لم توجد Policy صريحة.

  3. Sales policies تستخدم Ownership/Team membership داخل DB، لا filter في React.
  4. Rider policy تربط auth.uid() بـemployee→rider→active route assignment→service date.
  5. Kitchen projection لا يحتوي أصلاً على financial columns؛ المنع بالتصميم لا بالإخفاء البصري.
  6. Investor لا يصل إلى core tables؛ يصل إلى certified aggregate views وdocument grants فقط.
  7. كل SECURITY DEFINER له SET search_path، authorization داخلي، input validation، explicit grants، واختبار cross-role. الأصل هو Security Invoker.
  8. PUBLIC وanon وauthenticated لا يحصلون على EXECUTE ALL أو SELECT ALL.
  9. اختبارات سلبية تحاول الوصول المباشر عبر REST/RPC، لا تكتفي باختفاء زر.

Transaction اعتماد الدفع

يجب أن تكون الخطوات التالية داخل معاملة Database واحدة، مع SELECT ... FOR UPDATE على payment/invoice، وidempotency_key فريد:

confirm_payment(payment_id, idempotency_key, accounting_evidence_id, actor)
  1. authorize(actor, finance.verify_payment)
  2. lock payment + invoice
  3. if same idempotency_key already succeeded: return prior result
  4. require payment.state in {pending_verification, provider_confirmed}
  5. validate received amount, currency, reference uniqueness, evidence, bank/wallet account
  6. post payment_verified event
  7. allocate payment to invoice(s); prevent over-allocation unless on-account credit policy
  8. if invoice outstanding_balance == 0:
       mark invoice paid
       confirm order
       create subscription + first cycle + entitlement credits (once)
       create customer ownership assignment if absent
       create quota_credit event from eligible net collected amount
       create commission_accrual using effective policy version
       write outbox events: subscription.activated, sales.credit.posted, kitchen.demand.rebuild
  9. write audit correlation_id
 10. commit

أي خطأ يفشل كل المعاملة. لا يجوز أن تصبح الدفعة Verified بينما الاشتراك فشل إنشاؤه، أو أن ينشأ اشتراكان عند retry.

  • Reference الدفع فريد داخل provider/account/window، مع قواعد reconciliation.
  • Partial payment لا يفعل الاشتراك إلا إذا سمحت Credit policy مع حد وApprover.
  • Cash/COD لا يعد “مستلم لدى الشركة” عند تسجيل المندوب؛ هو Custody asset حتى handover والقبول.
  • Refund لا يعدل payment الأصلي؛ ينشئ refund/credit note/journal/reversal/commission clawback.

قواعد العمل والتحقق التفصيلية

العميل والـCRM

  1. Normalize رقم الهاتف إلى E.164 قبل البحث والإنشاء؛ إذا وجد Customer أو Lead مطابق يعرض Merge/Link، ولا ينشئ Duplicate صامتاً.
  2. لا يتحول Lead إلى Won إلا بحدث first_payment_verified أو approved credit؛ توقيع أو promise لا يكفي.
  3. Lead owner هو current Sales Agent افتراضياً؛ Manager يستطيع إعادة التعيين مع reason وتاريخ فعالية.
  4. كل محادثة/مكالمة/WhatsApp لها occurred_at وoutcome وnext action؛ “عدد المحادثات” يحسب Activities المؤهلة بتعريف metric، لا عدد فتح الشاشة.
  5. Lost reason إلزامي عند Closed Lost؛ لا يستخدم free text وحده بل taxonomy + notes.
  6. Customer dietary data تصنف Sensitive، وتعرض فقط لمن يحتاج تنفيذ الوجبة؛ لا تدخل marketing model دون Consent مناسب.
  7. Sales Agent لا يرى Customers بلا active assignment حتى لو عرف UUID؛ يجب أن يفشل API وRLS معاً.

الفاتورة والدفع

  1. Invoice issued غير قابلة للتعديل؛ أي تعديل يصدر Revision/Credit note وفق الحالة.
  2. Invoice number يولد من Sequence محمية، مثلاً EG-CAI-2026-000123، ولا يستخدم max()+1.
  3. total = subtotal - discount + delivery + tax يتحقق على Database، ويخزن currency.
  4. Payment proof ملف حقيقي في bucket خاص؛ MIME المسموح PDF/JPEG/PNG، حد حجم، hash، malware scan/validation، signed URL قصير.
  5. المحاسب لا يرى زر Verify قبل اكتمال evidence/reference/amount/account؛ الاستثناء يحتاج reason وController approval.
  6. لا يسمح بتأكيد Payment سبق تأكيده أو رفضه؛ retry بنفس idempotency يعيد نفس response، وبمفتاح جديد يفشل invalid_transition.
  7. المبلغ الزائد إما on-account credit بقرار أو Refund؛ لا يختفي في order amount.
  8. الدفع الجزئي يحدث Invoice إلى partially_paid؛ الاشتراك يبقى pending إلا approved credit policy.
  9. Settlement fees لا تنقص Revenue؛ تسجل مصروف gateway منفصل وفق Chart of Accounts.
  10. Cash عند Rider يمر collected_in_custody → handed_over → received_by_accounting → reconciled. لا يلمس Payment verified قبل Received.

الاشتراك والاستحقاقات

  1. لا ينشأ Subscription إلا مرة واحدة لكل activation source؛ unique activation_key.
  2. remaining meals/days يأتي من Entitlement ledger، لا total_days - consumed_days فقط.
  3. Pause Preview يعرض: effective date، أيام/وجبات المتأثرة، تاريخ الانتهاء القديم والجديد، أي رسوم/credit، وأثر cutoff.
  4. Pause يوقف/يزحزح future entitlement fulfilments غير locked. العناصر بعد cutoff تحتاج exception workflow؛ لا تعدل Kitchen batch بصمت.
  5. Auto-resume Job ينفذ عند pause_until، idempotent، ويولّد tasks إذا فشل.
  6. Indefinite pause لا يعد Churn حتى policy threshold؛ بعد threshold ينتقل إلى overdue_pause segment، لا يختفي من التقارير.
  7. Skip policy محددة في plan version: consume, shift, service_credit, أو forfeit; تظهر للموظف قبل التأكيد.
  8. Meal swap يتحقق من slot/size/allergens/capacity/cutoff/cost delta؛ exception يحتاج approval.
  9. تعديل Plan/size/address/window effective-dated؛ الماضي لا يعاد حسابه.
  10. انتهاء جميع entitlements/cycle يضع completed؛ Renewal ينشئ cycle جديد ويربط فرصة التجديد.

المطبخ

  1. Demand لا يدخل المطبخ إلا إذا Order eligible وEntitlement صالح وMenu published وداخل branch/date.
  2. Unique key على source entitlement + service_date + slot + unit sequence يمنع duplicate demand.
  3. لا silent fallback عند غياب menu أو recipe؛ يظهر Planning exception قبل cutoff.
  4. Batch lock بعد cutoff؛ التغيير بعده Event exception مع approver وwaste/cost impact.
  5. QA release إلزامي قبل ready_for_dispatch; failed critical check يضع batch/pack on hold.
  6. Kitchen view لا يحتوي sales price/payment/refund/commission columns في response أصلاً.
  7. Pack label يعرض أقل PII لازمة: customer short name/code، zone/stop، meal، size، strict exclusions؛ لا total paid.
  8. Actual yield، waste، rework، shortages تسجل كأحداث؛ لا تعدل planned quantity لتجميل variance.

التوصيل والـSLA

  1. لا يخرج Stop قبل QA release واكتمال pack scan أو exception approved.
  2. الحالات: planned→assigned→ready→dispatched→arrived→delivered أو failed; لا قفز إلى Delivered بلا POD/exception.
  3. client_event_id فريد لكل جهاز/حركة؛ retry offline لا يكرر الحدث.
  4. Device time وserver_received_at كلاهما محفوظان؛ anomaly إذا فرق الساعة يتجاوز threshold.
  5. Delivered terminal؛ الضغط المزدوج يعيد success السابق ولا يستهلك Entitlement مرتين.
  6. Failed يحتاج standardized reason، attempt، contact outcome، photo عند السياسة، وCX task.
  7. Rider لا يعدل sequence أو assignee إلا Permission منفصلة؛ Dispatcher يملك إعادة الترتيب.
  8. COD expected يأتي من open allocation لا order arbitrary amount. Collected amount يجب أن يطابق أو يسجل variance reason.
  9. POD policy configurable حسب قيمة/نوع العميل: OTP، توقيع، صورة، geofence.
  10. إغلاق Route يتطلب كل stops terminal، cash declared، packs accounted، وhandover task.

المحاسبة والإقفال

  1. كل Financial event يصدر balanced Journal أو ينتظر posting queue؛ لا Dashboard math بديل عن Ledger.
  2. Deferred Revenue as-of يعاد بناؤه من invoice allocation وrecognized performance؛ لا يعتمد على status الحالي فقط.
  3. Posted journal لا يعدل؛ correction عبر reversal + new entry.
  4. Month close يرفض إذا: unallocated payments، unreconciled cash، gateway settlement variances، negative entitlement anomalies، أو data-quality checks failed فوق tolerance.
  5. Reopen period يحتاج Controller + CEO/authorized approver، reason، audit.
  6. Finance يملك mapping COGS/Opex ويثبته في accounting policy version.
  7. CEO يرى PBT Margin لا يسميه Net Margin إذا قبل الضرائب.

محرك المؤشرات والمعادلات المالية

قاعدة قبل أي معادلة

كل KPI له سجل في metric_definitions يحدد: الاسم، المالك، grain، timezone، inclusion/exclusion، numerator query، denominator query، effective dates، version، certification rule. الداشبورد يعرض العدد والقيمة والنسبة، ويمنع القسمة على صفر بإظهار N/A لا صفر مضلل.

Active Members

العميل Active في لحظة القياس إذا لديه Subscription/Cycle مدفوع أو Credit-approved، وفيه Entitlement صالح غير منتهٍ، وحالته ليست canceled/completed. Pause بتاريخ عودة داخل السياسة يعرض منفصلاً ولا يعد Churn.

Active Members(as_of) = COUNT(DISTINCT customer_id meeting active policy at as_of)

يعرض: Active serving، Paused، Grace، New، Reactivated. لا يجمع Customer مرتين إذا لديه باقتان.

Subscription Revenue مقابل A-la-Carte

Recognized Subscription Revenue = SUM(posted revenue journal lines sourced from subscription entitlements)

Recognized A-la-Carte Revenue = SUM(posted revenue journal lines sourced from ad-hoc order items)

Subscription Mix % = Subscription Recognized Revenue / Total Eligible Recognized Revenue × 100

يعرض Collected cash منفصلاً؛ Prepayment ليس Revenue مكتسباً كله.

MRR وARR

MRR هو recurring-qualified normalized contract value في نهاية الفترة، لا إجمالي التحصيلات ولا A-la-carte.

MRR = Σ Active recurring subscription net contract value normalized to one month

مثال: باقة 24 يوم خدمة تغطي 30 يوم تقويمي حسب policy؛ لا تقسّم آلياً قبل اعتماد Definition. إذا العقد pre-paid لثلاثة أشهر، normalized monthly recurring value = net recurring contract value / 3، لا كامل الدفعة.

ARR = Closing Qualified MRR × 12

Closing MRR = Opening MRR + New + Reactivation + Expansion − Contraction − Churn

تستبعد: A-la-carte، delivery one-off، tax، refundable deposits، unverified invoices، paused خارج recurring policy، trial المجاني.

Deferred Revenue والإيراد المكتسب

يخصص Transaction price على Performance obligations/entitlements. أبسط سياسة عملية إن كانت كل وجبة/يوم متساوية داخل الباقة: سعر العقد الصافي المؤهل يقسم على مجموع وحدات الاستحقاق؛ لكن أي فرق جوهري في standalone selling price يحتاج allocation نسبي.

Allocated Unit Price = Net Transaction Price × (Unit SSP / Σ SSP of all promised units)

Recognized Revenue(as_of) = Σ Allocated value of fulfilled obligations with valid delivery/service evidence

Deferred Revenue(as_of) = Verified Allocated Consideration − Recognized Revenue − Refunds/Released Credits attributable to unfulfilled obligations

Delivery fee يعالج وفق Accounting policy: أداء مستقل أو ضمن الخدمة. Tax ليس Revenue. Pause لا يصفر Deferred؛ يزحزح توقيت الأداء. Failed/undelivered لا يعترف به إلا وفق سياسة مكتوبة ومراجعة المحاسب.

CAC

العميل الجديد في مقام CAC هو Customer فريد حدث له first_paid_at داخل الفترة بعد Finance verification. Order count ليس Customer count، والعميل العائد يعرض Reactivation CAC منفصلاً.

Fully-loaded CAC = (Media + Agency allocation + Creative + Influencer + Acquisition sales commissions + Promo subsidy) / First-time paying customers

Media CAC = Paid media spend / First-time paying customers attributed to paid media

Channel CAC = Eligible channel acquisition spend / First-time paying customers attributed to that channel

CAC Payback Months = Fully-loaded CAC / Average monthly contribution margin per new customer

يظهر First-touch وLast-paid-touch وBlended جنباً إلى جنب، مع attribution window الافتراضية 30 يوماً وقابلة للإصدار. يجب أن يطابق spend المعتمد حساب Finance ضمن 0.5% أو ينشئ data-quality incident.

LTV

لا يعرض النظام رقماً واحداً تجميلياً:

Realized Customer LTV = Cumulative posted contribution margin from customer to as_of

Cohort Realized LTV at month n = Cohort cumulative contribution through month n / Customers acquired in cohort

Contribution = Net recognized revenue − Food − Packaging − Delivery variable cost − Payment fees − Variable service cost − Refunds/credits expense

Simple Modeled LTV = Monthly ARPA × Contribution Margin % / Monthly Logo Churn

LTV:CAC = Contribution-margin LTV / Fully-loaded CAC

Modeled LTV يحمل forecast وconfidence/maturity، ويعرض Sensitivity عند churn 6%/8%/10% مثلاً. لا يستخدم Gross Revenue LTV لتقييم قناة في نشاط توصيل غذاء منخفض الهامش.

Churn وRetention وRenewal

هذه ثلاثة مؤشرات مختلفة:

Logo Churn % = Opening active customers who churned during period / Opening active customers × 100

Churn event: cancellation/expiry بعد grace policy بلا renewal/reactivation. Pause المحدد لا يعد Churn. يعرض العدد بجانب النسبة وحسب channel/plan/zone/cohort/tenure/reason.

Logo Retention % = (Opening active customers − Opening customers churned) / Opening active customers × 100

Gross Revenue Retention = (Opening recurring revenue − Churn − Contraction) / Opening recurring revenue × 100

Net Revenue Retention = (Opening recurring revenue − Churn − Contraction + Expansion) / Opening recurring revenue × 100

Renewal Rate % = Due subscription cycles renewed within grace window / Eligible cycles due in period × 100

المقام في Renewal هو Due population، لا كل الاشتراكات. يعرض التجديد العددي والقيمي، On-time وLate، وAuto/manual.

Conversion والمحادثات

Paid Conversion % = Unique first-time paying customers from eligible leads / Eligible qualified leads × 100

Speed-to-lead = first human response_at − lead_created_at

“Conversation count” يحتاج تعريفاً يمنع تضخيم الرسائل الآلية: Conversation مؤهلة فيها outbound/inbound human interaction أو activity outcome، لا كل message.

Gross/Contribution/PBT

Gross Margin % = (Net Recognized Revenue − Defined COGS) / Net Recognized Revenue × 100

Contribution Margin % = (Net Revenue − Food − Packaging − Delivery variable − Payment fees − Variable service/refunds) / Net Revenue × 100

PBT Margin % = Profit Before Tax / Net Recognized Revenue × 100

لا تسمى نسبة 8–10% قبل الضريبة Net Margin في شاشة المستثمر؛ تسميتها PBT Margin.

Delivery SLA

الأحداث الدنيا: ready_at, assigned_at, dispatched_at, arrived_at, delivered_at, failed_at مع promised window snapshot.

Gross On-time % = Successful deliveries completed within promised window / Eligible successful deliveries × 100

Adjusted On-time % = On-time eligible deliveries / Eligible deliveries after documented exclusions × 100

Dispatch Dwell = dispatched_at − ready_at

Last-mile Time = delivered_at − dispatched_at

SLA Breach Minutes = MAX(0, delivered_at − promised_window_end)

يعرض P50 وP90 حسب Zone/Window/Rider، لا average فقط. كل استثناء customer-caused/force majeure يبقى ظاهراً في Gross ويظهر سبب استبعاده في Adjusted.

Plan vs Actual وForecast

Variance Amount = Actual − Approved Plan

Variance % = (Actual − Plan) / ABS(Plan) × 100

Required Run-rate = (Year Target − YTD Actual) / Remaining Eligible Periods

Forecast Gap = Forecast Closing Value − Target Closing Value

Plan version بعد approval لا يعدل؛ أي reforecast نسخة جديدة مع reason. تعرض Dashboard Current plan وLatest forecast كخطين منفصلين.

Sales Quota وCommission

Quota Credit = Net verified collected amount allocated to eligible invoice lines in target period

Attainment % = Period quota credits / Effective target × 100

Commission Accrued = Σ Eligible quota credit × Effective tier rate/policy rule

Commission Payable = Vested accruals − Approved clawbacks − Prior advances

Renewal credit وnew acquisition credit وA-la-carte يمكن أن تكون لها rules مختلفة. Refund ينشئ negative posting في فترة الحدث مع link للأصل، ولا يعدل تاريخ الشهر القديم دون Close policy.

حالات قبول حرجة بصيغة Given/When/Then

AC-01 — بيع مدفوع وتفعيل ذري

Given مندوب يملك العميل، وفاتورة صحيحة 4,628 + 50 توصيل − 100 خصم = 4,578 جنيه، وإثبات فعلي.
When المحاسب يطابق 4,578 ويؤكد.
Then داخل commit واحد: Payment verified، Invoice paid، Order confirmed، Subscription/Cycle/Entitlements مرة واحدة، customer assignment، quota credit 4,578 أو القيمة المؤهلة حسب policy، commission accrual، outbox؛ وتفشل الرحلة كلها إذا فشل أي جزء.

AC-02 — Double click / Retry

نفس Idempotency-Key مرتين يعيد نفس IDs؛ مفتاح جديد لمحاولة Verify على Payment terminal يرفض. لا duplicate subscription أو quota أو fulfillment.

AC-03 — Partial payment

Payment أقل من balance يجعل Invoice partially_paid ولا يفعل Subscription، إلا approved credit موثق. Dashboard يفرق collected/outstanding.

AC-04 — Sales ownership

Sales A لا يرى Customer B في UI أو API أو direct table/RPC، حتى مع UUID صحيح. Sales Manager يرى فريقه فقط. CEO/authorized يرى حسب policy.

AC-05 — Kitchen data minimization

Kitchen response لا يحتوي invoice/payment/discount/commission keys، ويعرض demand بعد Finance activation فقط.

AC-06 — Pause shift

Pause من 10 إلى 14 سبتمبر يعرض Preview، يلغي/يزحزح fulfillments غير locked، يحفظ balance، ويحدث expected end. لا يحسب Churn. Resume job idempotent.

AC-07 — Skip policy

خطة shift عند Skip تضيف entitlement/fulfillment بديل في نهاية الجدول؛ خطة forfeit تخصم فقط بعد تأكيد واضح. Ledger يفسر الرصيد.

AC-08 — Delivery offline

Rider offline يسجل dispatched/arrived/delivered مع OTP وصورة؛ عند الاتصال تعاد الحزمة مرتين. Server يقبل كل event مرة واحدة، يحافظ على device/server times، ولا يستهلك entitlement مرتين.

AC-09 — Invalid state

Delivered بلا ready/dispatch/POD يرفض، Ready بلا QA release يرفض، Refund بلا Payment/approver يرفض، Kitchen change بعد cutoff يطلب exception.

AC-10 — Cash custody

تسجيل Rider للتحصيل لا يغير Payment إلى verified. بعد handover dual-sign وFinance receive يصبح cash received؛ variance لا يغلق بلا reason/approval.

AC-11 — Deferred revenue

فاتورة مدفوعة 24 استحقاقاً؛ بعد تسليم 6، recognized/deferred يطابق allocation policy. Pause لا يعترف بإيراد جديد. Refund لغير المنفذ يحدث liability والjournal والcommission clawback.

AC-12 — MRR vs A-la-carte

A-la-carte مدفوع لا يدخل MRR/ARR. اشتراك pre-paid 3 أشهر يدخل normalized monthly value فقط. Drill-down يبين كل line.

AC-13 — Churn/Renewal

Pause محدد لا يدخل churn؛ Cycle due لم يجدد ضمن grace يدخل denominator وchurn حسب policy؛ Reactivation لاحقة Event مستقل ولا تمحو التاريخ.

AC-14 — CAC dedupe

عميل له ثلاثة Orders في أول شهر يعد مرة واحدة. Customer merge لا يضاعف المقام. Full refund/zero-price trial يعالجان وفق definition test fixtures.

AC-15 — Sales commission

Finance confirmation ينشئ quota فوراً. Policy version الصحيحة حسب التاريخ تستخدم. Refund ينشئ reversal/clawback linked، ولا يعدل حدث الأصل.

AC-16 — SLA

ready/assigned/dispatched/arrived/delivered مكتملة. Gross/Adjusted وP50/P90 يعاد حسابها من نفس events؛ الاستثناء يبقى ظاهراً ويحتاج reason.

AC-17 — Investor privacy

Investor API/exports لا يحتوي customer_id القابل للعكس أو name/phone/address/dietary؛ كل view/download watermarked ومدقق، وaccess expiry يعمل.

AC-18 — Month close

لا يغلق الشهر مع unallocated payment أو cash variance أو unbalanced journal. بعد الحل، debit=credit وDeferred roll-forward وbank reconciliation ضمن tolerance، ثم snapshots Certified.

AC-19 — RLS red-team matrix

لكل دور محاولات SELECT/INSERT/UPDATE/DELETE/RPC على كل domain. كل deny متوقع يفشل فعلياً. لا function SECURITY DEFINER ترجع صفوفاً خارج scope.

AC-20 — Migration

Counts والعملاء الفريدون والمدفوعات والإيراد المؤجل وأرصدة الاستحقاق تطابق ملف reconciliation؛ كل فرق له exception record. Rollback dry-run ناجح.

MANDATORY ACCEPTANCE SCENARIOS
- Finance-confirmed payment atomically creates exactly one paid invoice state, subscription/cycle/entitlements, customer ownership, quota credit, commission accrual, audit, and outbox.
- Partial payment does not activate without approved credit.
- Duplicate payment webhook/verify request does not duplicate any result.
- Sales Agent cannot read another agent’s customer by UI, API, table, or RPC; Kitchen cannot read finance; Rider cannot read another route; Investor cannot access PII.
- Pause/skip/renew recalculates entitlement balances and expected end correctly, with no false churn.
- Offline Rider replay with POD and cash is idempotent and preserves event order/time.
- Deferred revenue, recognized revenue, refund, credit, and commission reversal reconcile to journal entries.
- Month close blocks material unresolved differences and produces certified snapshots.
- CAC/LTV/churn/renewal/MRR/ARR show correct numerator/denominator for fixed fixtures.
- Production demand is neither missing nor duplicated and QA gates dispatch.
- Restore drill and rollback procedure are demonstrated in staging.

DEFINITION OF DONE
A feature is not done until: business owner accepts its rule; authorization and negative RLS tests pass; money/state/idempotency tests pass; Arabic responsive UI and accessibility pass; audit/observability are present; documentation is updated; migration works from empty and prior schema; and no P0/P1 issue remains. Acceptance is based on executable scenarios and reconciled totals, never screenshots alone.

STOP CONDITIONS
Stop and escalate instead of guessing when accounting policy, tax treatment, commission tiers/vesting, cancellation/refund policy, pause/skip entitlement behavior, delivery windows, cutoff times, or legal/privacy requirements are not signed off. Implement them as versioned configuration after decision. Do not bury unresolved policy inside code.
